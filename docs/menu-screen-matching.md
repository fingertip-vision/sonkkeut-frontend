# 음성 주문과 OCR 메뉴 연결 — Kotlin 0.2.4

별도 AI 서버 없이 현재 Android 앱에서 처리한다. 기존 백엔드는 매장별 메뉴와 별칭을 제공한다. 앱의 메뉴 DB/검색 정보와 OCR은 동일한 메뉴 식별자를 기준으로 연결한다.

## 처리 순서

1. 백엔드 메뉴를 내려받아 서버 주소·매장 코드·상품 ID로 식별한다. 상품 ID가 없는 기존 API는 정식 메뉴 이름을 사용한다. 매장이 바뀐 주문 ID는 재사용하지 않는다.
2. 음성 주문의 정식 이름·별칭·관련 표현으로 메뉴 후보를 찾고 사용자가 주문을 확인한다. 관련 표현은 후보 추천용이며 상품 동등성이나 재료를 보장하지 않는다.
3. 주문에는 확인한 메뉴 ID를 보관한다. OCR로 읽은 메뉴와 옵션 화면의 이름을 같은 매장 카탈로그와 비교한다.
4. Unicode/띄어쓰기/줄바꿈/원화 가격을 정규화한다. 정식 이름을 우선하고, DB에 등록된 별칭은 같은 상품으로 연결한다.
5. 네 글자 이상 이름의 한 글자 오탈자 또는 기존 버튼 안에 포함된 여러 줄의 결합은 사용자 확인을 요구한다. 화면 글자와 주문 이름을 함께 읽고 화면에도 확인 창을 표시한다.
6. 동일 이름이 여러 위치에 보이거나 근접한 상품 후보가 여러 개면 선택을 보류하고 근접 재읽기를 제안한다. 읽기 불확실·잘못된 좌표·상품 구분어 누락은 위치 안내의 근거로 사용하지 않는다.
7. 사용자 확인은 카탈로그·화면 종류·글자·요소 ID·좌표에 묶인다. 화면이 바뀌면 과거 확인을 재사용하지 않는다. 확인 이후에도 새 프레임으로 위치를 읽는다.

예: 사용자 ‘크림 파스타’ → 관련 표현 검색 → ‘까르보나라’ 후보 확인 → 해당 메뉴 ID → OCR ‘까르보나라’ 위치. ‘크림 파스타’가 실제로 같은 상품일 때만 관리자 별칭으로 등록한다. 크림 파스타가 여러 종류면 후보를 선택하게 한다. 관련성만으로 다른 메뉴 버튼을 누르도록 안내하지 않는다.

## 변경 영역

- AI 라이브러리: `ScreenMenuResolver`, `MenuDocument.id`, 메뉴/옵션 OCR 원문 유지.
- 프론트: `MenuScreenLinks`, 주문 ID 보관, 화면 탐색·옵션 검사 공통 매칭, 음성/화면 확인, 메뉴·설정의 ‘메뉴 인식 진단’.
- 기존 백엔드 API 변경이나 AI 서버 배포는 필요하지 않다. 모델 가중치와 음성 모델 다운로드 구조는 그대로다.
- 진단은 현재 세션의 인식 글자·상품 ID·매칭 근거를 표시한다. 영상·음성·진단 문장을 추가로 서버에 보내지 않는다.

## 한계와 다음 판단

이것은 사전학습 임베딩 또는 LLM RAG가 아닌 매장 카탈로그 기반 로컬 검색/매칭이다. 가려진 글자, 두 글자 이상 손상, 읽기 불확실한 OCR은 자동 보정하지 않는다. 실제 매장별 실패 사진·정답 상품·인식 글자로 평가해야 실사용 개선 정도를 판단할 수 있다. 점수는 확률이 아니다. 실물 키오스크와 사용자 휴대폰의 성공률을 검증한 것으로 해석하지 않는다.

향후 여러 문장으로 된 주문 해석이나 대규모 메뉴 지식 검색이 필요할 때만 서버 보완을 고려한다. 그 경우 앱 → 백엔드 → AI 서버로 연결하고, AI는 현재 매장 카탈로그 안의 메뉴 ID 후보와 근거만 반환한다. 앱이 화면 존재·좌표·사용자 확인을 최종 검사한다. AI 서버가 추측한 좌표를 바로 안내에 사용하지 않는다.

## 검증

신규 회귀 테스트: 가격/줄바꿈, 별칭, 한 글자 손상, 상품 구분어, 공유 별칭, 품절 상품 이름 우선, 경쟁 후보, 중복 위치, 잘못된 좌표, 버튼 내부 줄 결합, 인접 카드 분리, 매장 ID 분리, 화면 변경 시 확인 무효화, 옵션 동일성, 음성 주문 ID 보존. 실제 기기 음성·키오스크 시험은 별도 필요하다.
